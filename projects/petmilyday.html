Overview

개요 · 왜 만들었는지

반려동물 보호자가 동물병원 검색·예약부터 쇼핑, 중고거래, 커뮤니티, AI 자가진단까지 하나의 서비스에서 이용할 수 있는 반려동물 통합 케어 플랫폼입니다. 흩어져 있던 반려동물 관련 서비스를 한곳으로 모으는 것을 목표로 했습니다.

전체 엔티티 37개 · API 187개 규모의 Spring Boot 모놀리식 웹 애플리케이션이며, 저는 동물병원·예약 도메인을 중심으로 인증·실시간 알림·AI 연동 등 서비스 전반의 공통 기능을 담당했습니다.

Problem Solving

문제 해결

① 동일 시간대 중복 예약
Problem같은 시간대에 동시 요청이 들어오면 동일 슬롯에 중복 예약이 발생할 수 있었습니다.
Cause예약 등록 시 동시성 제어가 없어, 여러 트랜잭션이 같은 슬롯을 함께 조회하고 각각 기록했습니다.
Solution등록 시 병원 엔티티를 비관적 락(PESSIMISTIC_WRITE, findByIdForUpdate)으로 조회하도록 락 적용 순서를 설계했습니다.
Result동시 요청 경합 상황에서도 중복 예약을 방지하고 예약 정합성을 보장했습니다.
② 승인해도 반영되지 않던 예약 — "성공 응답 ≠ 정상 동작"
Problem병원 관리자가 예약을 승인해도 목록에는 계속 '대기'로 남았습니다. 화면은 오류 없이 넘어가고 에러 페이지도 없었습니다.
Cause네트워크→DB→SQL 로그를 단계별로 좁혀, 조회한 엔티티 상태값은 바꿨지만 서비스 메서드에 트랜잭션이 없어 변경 감지(dirty checking)가 동작하지 않아 UPDATE가 실행되지 않음을 확인했습니다.
Solution해당 서비스 메서드에 @Transactional을 적용해 변경 사항이 정상 반영되도록 수정했습니다.
Result승인 상태가 정상 반영됐고, 이후 "요청·쿼리·저장 결과를 단계별로 직접 확인하는" 습관을 갖게 됐습니다.
Why

기술 선택 이유

WHY비관적 락

예약은 충돌 시 재시도가 사용자 경험을 해치고 경합 빈도도 낮지 않아, 재시도 기반 낙관적 락보다 처음부터 직렬화하는 비관적 락이 적합하다고 판단했습니다.

WHYJWT + HttpOnly 쿠키

localStorage 저장은 XSS로 토큰이 노출될 수 있어, JS 접근이 불가한 HttpOnly 쿠키에 저장하고 SameSite=Lax로 CSRF를 완화했습니다.

WHYQueryDSL

키워드·진료과목·응급여부처럼 선택적 조건이 조합되는 검색에서 null 조건 자동 무시가 필요해, 타입 안전한 동적 쿼리를 선택했습니다.

WHYSSE (vs WebSocket)

알림은 서버→클라이언트 단방향으로 충분해, 양방향 연결을 유지하는 WebSocket보다 가벼운 SSE를 선택했습니다.
